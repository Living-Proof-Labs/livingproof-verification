# Verification index and history — human-readable view

Design mock for the public docs pages:

- Index: https://docs.livingprooflabs.com/livingproof-verification/index.html
- History (the page in the feedback): https://docs.livingprooflabs.com/livingproof-verification/booster-t1/stock-mujoco-corner/
- History used in this mock (so failures can be shown): `booster-t1/stock-mujoco-hallway`

The pages are generated by `tools/site.py` in [Living-Proof-Labs/livingproof-verification](https://github.com/Living-Proof-Labs/livingproof-verification). `render()` writes the index and each variant’s history from `run.json`. The styled run page itself is rendered by the capability reporter; this change is about the index and history chrome, not the report body.

Open `index.html` for the review, or the standalone pages `reports.html` and `history.html`.

## What’s wrong today

Both pages are unstyled HTML tables. A history row currently looks like:

```
44241798449 | CI run 44241798449 | 2026-11-18T05:13:39Z | PASS 1/1 passed (1 needed) · walk-corner | 2363e612dc0c | SHA256SUMS
```

The run id appears twice. The CI column is not a link (`ci_run()` in `tools/site.py` writes it as plain text on purpose). The timestamp is raw UTC. The outcome buries the result in counts. The commit is a SHA of `livingproof-verification`, which has no tags. Checksums are in every row. Nothing says who posted the entry, and failures do not name the evaluators that spoke. On a narrow screen the table overflows.

## Design principles

Results first. Evaluators stay quiet and only failures speak. Details open on demand (the report, or a chip into the evaluator that failed). Evaluator titles are used exactly as stored (`display_name`), with no “Evaluator” suffix — the Scenario evaluator is **Scenario**. Each human reviewer who reports a problem is their own chip (and their own card on the report).

The visual language matches the capability report: navy masthead, teal accent, DM Sans, `--bg-muted` / `--border-strong` hover, pass/fail chips, a `--speak` tint for findings.

The list stays continuous, with no pagination. History will be pruned holistically elsewhere (GitHub pipelines are not a long-term archive).

No backfill is required. Going forward, new records store the richer fields. Older rows simply omit what they don’t have.

## Fields shown

### Index (one row per robot / scenario)

| Shown | Source | Notes |
| --- | --- | --- |
| Outcome badge | `outcome[].grade` | Plain **PASS** / **FAIL** / **Not supported**. No “1/1 passed (1 needed)”. |
| Scenario title | capability, as a readable name | “Walk the hallway”, “Walk around the corner”. Variant becomes a subtitle: `stock · MuJoCo`. |
| Failing evaluators | new `failing_evaluators[]` | Linked chips, failures only. Omitted when the list was not stored. |
| Release | new `commit.tag`, else short SHA | Fallback is 8-character SHA, visually quieter than a tag. |
| When | `run.created` | Relative text (“20 minutes ago”) with `datetime` in a `<time>` element. Full local date in the tooltip, Australia/Sydney. |
| Links | existing paths | “Latest report” and “History (N)”. No CI run number. |

Rows are grouped by robot. A short status line counts how many latest results failed.

### History (one entry per run, newest first)

| Shown | Source | Notes |
| --- | --- | --- |
| Outcome badge | `outcome[].grade` | Plain PASS / FAIL. |
| Scenario title | capability name | |
| Failing evaluator chips | `failing_evaluators[]` | Each chip uses the exact title and links to the report at `#evaluator-<id>`. |
| One-line finding | optional `failing_evaluators[].summary` | Only when a failure spoke. A quick view; the report has the rest. |
| Release tag | `commit.tag`, else short SHA | |
| When | `run.created` | Relative + local tooltip, as on the index. |
| Who posted | new `poster` | `CI`, an agent name, or a human name. If missing, treat as CI. |
| Report | `runs/<id>/` | Primary link. The run id is not shown as text. |
| CI run | `run.url` | The words “CI run” only — no number. See the Actions-link note below. Not shown for a human post that has no CI run. |

### Dropped from the list

- Raw run id (both the “Run” column and the number after “CI run”).
- Checksums / `SHA256SUMS`. The file stays in the run folder and can remain linked from the report or provenance, just not from the history list.
- ISO-Z timestamps as the visible text.
- Outcome counts and capability slugs in the summary line (“PASS 1/1 passed (1 needed) · walk-corner”).

### Header (history page)

- Breadcrumb back to the index.
- Readable title: robot, configuration, scenario (“Booster T1 · stock · Walk the hallway”), not `booster-t1 · stock-mujoco-hallway · run history`.
- Tool pins already use release tags (specs, runner, verifier, reporter). Keep them as quiet metadata.
- Robot pin: show a git tag when the pinned commit has one. Today `a00c7d884b76` **is** `v2.2.10` on `livingproof-booster-t1`, but the live page prints the SHA. Fall back to a short SHA only when there is no tag. Also show the software version (`stock 1.0.0` from `summaries[].system.version`) when known.

## Fallbacks (and no backfill)

| Missing field | What to show |
| --- | --- |
| No `commit.tag` | Short SHA (8 characters), muted, still linked to the commit. |
| No `robot.tag` | Short robot SHA in the header. |
| No `failing_evaluators` | No chips, even if the run failed. Do not parse old `report.json` unless it is cheap and already in hand at publish time for the *new* run. |
| No `poster` | “CI”. |
| No finding summary | Chips only, no one-line excerpt. |
| `UNSUPPORTED` | Badge “Not supported”, no chips. |

The mock shows this mix on purpose: example tagged rows at the top, then live untagged SHA rows, with chips only where the new field would exist.

## What the pipeline should record going forward

Extend `run.json` (written by `add_run()` / `provenance()` in `tools/site.py`). Suggested shape:

```json
{
  "commit": {
    "sha": "2363e612dc0ccae45cf8726134e657005060b326",
    "url": "https://github.com/Living-Proof-Labs/livingproof-verification/commit/2363e612…",
    "tag": "v1.0.0"
  },
  "robot": {
    "repository": "Living-Proof-Labs/livingproof-booster-t1",
    "commit": "a00c7d884b764c89404dc91be9232c0d55eb392c",
    "tag": "v2.2.10",
    "configuration": "stock",
    "software_version": "1.0.0",
    "url": "https://github.com/Living-Proof-Labs/livingproof-booster-t1/releases/tag/v2.2.10"
  },
  "poster": {
    "type": "ci",
    "name": "CI"
  },
  "failing_evaluators": [
    {
      "id": "livingproof-scenario",
      "title": "Scenario",
      "href": "#evaluator-livingproof-scenario",
      "summary": "Drifted 0.66 m from the centreline, then touched the right wall at 7.80 s."
    }
  ]
}
```

- `commit.tag` is a git tag on the **livingproof-verification** commit that produced the run, when one exists. That repo has **no tags today**, so every current row will use the SHA fallback until tagging starts (or until another agreed identifier is chosen — see Open questions).
- `robot.tag` can be resolved at publish time by matching the locked robot commit to a tag. This is already possible for the current pin (`v2.2.10`).
- `software_version` comes from the report’s `summaries[].system.version` (`stock` `1.0.0` on the 18 Nov hallway run). It is not in `run.json` today.
- `poster.type` is `ci`, `agent`, or `human`. `name` is “CI” or the poster’s display name.
- `failing_evaluators[].title` is the evaluator `display_name` exactly. Include an evaluator only if it spoke (failed or filed a finding). One chip per evaluator, even if several trials failed. Each human reviewer is a separate entry. The chip links to a **stable report anchor** `#evaluator-<id>`. The run report today only exposes `id="summary"`; the reporter should start emitting these anchors.
- `summary` is one short sentence for the list, not the full trial table.
- `run.url` is already stored (the Actions URL). `run.created` and the grade are already stored.
- Checksums continue to be written into the run folder; they are just not listed.

## CI run links vs the current Actions policy

`run.url` is already on the record, but the public site refuses to link to GitHub Actions: `ci_run()` renders unlinked text, and `public_page_problems()` fails the build if published HTML contains `/actions/`. That policy exists because Actions artifacts need a GitHub sign-in and then expire; evidence is copied onto the docs site instead.

Aaron asked for the CI run to be a link without the number. The mock does that: the word **CI run** points at `run.url`, and **Report** points at the published run page (the thing a person should open first).

Implementing the CI link means carving an exception in that lint for the index/history pages only — not re-introducing Actions artifact download links on the report. If the policy should stay strict, drop the CI run link and keep only **Report**.

## Accessibility

- Outcome is a text badge, not colour alone.
- Links have visible names: “Latest report”, “History (79)”, “Report”, “CI run”, or the evaluator title. The run id is not required to understand the link.
- Times use `<time datetime="…">`.
- Evaluator chips include a `title` (and should have an accessible name) such as “Open the Scenario finding in the report”.
- `:focus-visible` uses the teal focus ring.
- Hover/selection changes are not the only cue; reduced-motion drops the colour transition.
- On small screens the layout stacks; nothing relies on a wide table.

## Open questions

1. **Which release tag did Aaron mean?** The history “Commit” column is the `livingproof-verification` SHA, and that repository has no tags. Meanwhile the robot pin already has `v2.2.10`, and the report already knows `stock 1.0.0`. The mock treats a verification-repo tag as the per-row release (SHA fallback until tags exist) and also shows the robot tag and software version in the history header, which is a cheap win today.
2. **May the public history link to Actions?** See the policy note above.
3. Related existing issue: [#25 Run history with “conditions changed” flags](https://github.com/Living-Proof-Labs/livingproof-verification/issues/25) — complementary, not a substitute for this readability pass. The header today also shows the *newest* run’s tool versions for the whole list; per-row pins would matter if those flags land.
